# 已验收原型的等价迁移

以已发布并验收的版本为对照。登记三类差异：文案、内容值、可见顺序和有效 URL 须与源站一致；正式域名、构建资源路径和水合标记可随环境变化；字体、样式、响应式行为、功能取舍和旧路径重定向须有批准记录。以下步骤依次使用同一份项目迁移记录。

## M0 固定源版本与对照样本

- 记录已发布版本、源域和导出 commit 或 ZIP。让原型仓保持只读。由路由定义和内容数据枚举有效路径、动态 slug 及语言版本，登记默认语言、fallback、语言切换方式和原有 404 行为。
- 从已发布域用浏览器打开每个 URL，等待内容稳定，在桌面 1440×900 和移动 390×844 分别保存最终 DOM、可见文本、截图及页面 SEO 字段。逐文件确认存在且非空。预先标记时间戳、轮换内容与平台徽章等可过滤区域。
- 盘点表单、邮件、登录权限、数据库、存储、API、支付回调、搜索、分析与同意机制、Webhook、定时任务及后台。逐项记录迁移、替代或排除，写明目标实现、用户入口如何处置及对应验收用例。
- 清洗源码、DOM 和截图中的密钥、内部地址及个人信息。归档排除环境文件、Git 历史、依赖、缓存和构建产物，大文件另存。验证归档目录已排除在部署构建上下文之外。

## M1 确定内容与部署方案

在目标仓记录选择和理由，后续阶段直接复用。

| 决策 | 选择依据 |
|---|---|
| 内容存储 | 经常编辑的文章采用 Markdown + frontmatter；多语言营销字段采用 JSON + Zod；已有强类型常量且主要由开发者维护时保留 TS 模块。混合站按内容类型选择。 |
| 部署产物 | 全部能力支持预生成时可静态导出；需要请求时执行的 API、SSR 等能力时选择 Node standalone、Vercel 或兼容的边缘运行时。standalone 打包包括 public 和 .next/static；Cloudflare 部署须确认锁定版本的 OpenNext 兼容性。 |
| 部署位置 | 记录独立目标仓、包管理器、正式域及挂载路径。主域子目录反代须明确内容路径和 /_next 静态资源分别由哪个服务响应，必要时使用独立资源域。 |

## M2 建立可构建的目标仓

用原型的类型检查结果作基线。建立最小 App Router 工程，保留 Tailwind 主版本，按实际依赖初始化组件库、PostCSS 与锁文件。核对 CSS 文件搬移后的字体、@source、@import 相对路径。空站生产构建通过后再搬页面。多人分工按 import 依赖划分，共享模块指定唯一修改方。

## M3 转换内容

枚举文件和路由内联的内容来源，按 M1 决策转换格式。逐字段比对键、值、顺序和多语言覆盖；将 schema、slug 唯一性及资源引用校验接入构建，让缺失项直接报错。

## M4 迁移静态资源

从导出包、已发布域资产清单或 JS bundle 解析图片、图标和字体。核验文件类型和尺寸，避免保存错误页。移除文件名哈希时处理重名并同步引用。字体本地托管。通过构建产物和运行时请求确认已切断原型平台依赖，记录 M0 批准保留的外部服务。

## M5 迁移页面与运行能力

按布局壳、页面、共享组件迁移。基础路由与组件写法见 [代码转换参考](code-rewrite.md)。对照 M0 补齐以下容易被构建检查漏掉的行为：

- 静态页面枚举完整参数集，保留段级自定义 404。验证未知 slug 和无 JavaScript 时的可见正文。
- 替换 import.meta.glob 时，客户端可达模块须能在浏览器运行。静态图片导入若传给只接受 URL 的组件，取其 src。构造交互回调的组件与接收方须处于可传递该回调的客户端边界。
- 为服务端函数确定 API 归属。迁移校验 schema、HTTP 方法、响应状态、Range 透传及已知业务错误提示；内部异常只记服务端日志。平台网关改为目标环境配置，密钥留在服务端。
- 使用生产构建验证路由与运行能力的实现位置。项目自己的平台依赖同时检查包清单、源码导入和环境配置。

## M6 核对搜索入口

沿用已验收的逐页 SEO 字段与 JSON-LD，检查页面级 openGraph 覆盖布局时是否丢失公共字段。按 M0 清单对比 title、description、H1、canonical、robots 与 sitemap。涉及多语言 URL 架构调整时，按 [multilingual-site-build](https://github.com/kostja94/vibe-coding/tree/main/skills/multilingual-site-build) 建立并验证映射。保留源站尾斜杠策略。

## M7 验证等价性

先用预期 title 或 H1 确认测试端口确实指向目标站，再复用 M0 的 URL、视口及样本。把逐页明细写入文件，记录实际覆盖数与预期覆盖数。

| 检查 | 通过条件 |
|---|---|
| 文本 | 逐页逐视口比较渲染后的 innerText，过滤已登记区域后差异为零。失败项附缺失行、新增行和上下文。 |
| 视觉 | 比较对应截图，逐项复核超阈值差异，特别检查字体、折行、断点和布局偏移。所有差异都有处置记录。 |
| 交互与运行 | 执行 M0 能力用例，覆盖成功和失败路径、导航及移动交互。批准排除的功能按约定处置；控制台错误和未获准的失败请求为零。 |

## M8 上线与交接

在部署预览域复跑 M7。按实际嵌入、设备权限和第三方服务需求核对安全响应头。通过后按既定域名方案切换并保留回退入口。上线后 48 小时内巡检有效 URL、重定向和线上能力，提交 sitemap。将决策、测试证据和上线结果归入部署仓，后续维护从该仓继续。
